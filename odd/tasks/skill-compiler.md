# Skill Compiler — compile skills to .so plugin graphs

Feature: turn Waku skills from prompt text into compiled .so plugin graphs.
Decisions (2026-11-17): LLM proposes graph, human approves; worker-apart by default; Nim optional with text fallback.

## Specs

S1: A skill graph is a JSON manifest with the same schema as plugin manifests (ABI v1), restricted to kinds `llm` and `router` only, needs ⊆ {llm}, prompts as plain strings with {{key}} placeholders. No tool/agent kinds — worker-eligible by design. Router routes may carry an optional `when` condition {key, op, value} with a closed op catalog: len_gt, len_lt (int value), eq, contains (string value). Routes are evaluated in declaration order, first match wins; if no condition matches, the router makes an LLM fallback call that must answer exactly one declared label (unknown label = loud error). Because the fallback always exists, every router must declare needs ["llm"].

S2: The validator (T1) is the security boundary: it checks schema, allowed kinds, needs, route destinations (END or manifest nodes), unique route labels, `when` condition shape (op in catalog, value type per op, non-empty key), routers declare needs ["llm"], and that the graph is a DAG reachable from the first node (no cycles).

S3: Compilation uses a fixed Nim template (mirroring fixture_plugin_textops.nim ABI: waku_plugin_init/describe/node_run/string_free). The LLM never writes Nim code — only the JSON manifest changes between skills.

S4 (corrected): Compilation runs in a child process with a timeout and a minimal environment: PATH and HOME, nothing else, so no key or WAKU_* variable reaches the compiler. It does NOT restrict the network - the child runs as the user on their own machine, and a socket sandbox was never implemented. Anyone reading the earlier wording would have believed a guarantee that does not exist. Output: ~/.waku/skills-compiled/<name>-<hash>.so where hash is of the canonical graph JSON.

S5: If a .so for the graph hash already exists, load it directly (no recompile). Loaded .so files are never unloaded (process lifetime, per plugin contract). New skill version = new hash = new .so file.

S6 (corrected): A compiled skill runs as a headless plugin worker through `pluginRunHeadless`; `runPluginWorker` is the worker-role child-line wrapper, not the call the loop makes. In-process loading only when a human selects the assembled `plugin:<name>` graph.

S7: If Nim is not available at runtime, skills fall back to text mode (current behavior). No hard dependency on the Nim toolchain.

S8 (SUPERSEDED by S15, not implemented): shadow mode would have compiled out of band. The binary is synchronous and single-threaded by policy, so S15 replaced it: the loop uses an installed plugin and never compiles. Keep this line only to explain why nothing in the loop starts a compiler.

S9: The validator also checks data flow, not just structure: every `{{key}}` in a prompt must be a key the node reads (`inKeys`) or `message`; every `inKeys` entry must be produced by an earlier node's `outKey` or be an input state key (`message`, `mem_text`); a node whose `outKey` is empty must not be read by anyone. An incoherent graph is refused loudly instead of interpolating an empty string.

S10: The generated router fallback must run at most once per router visit per run. The engine calls the node fn AND the route fn for one router visit, so a fallback decided in the shared node path would pay twice and could answer differently. The decision is memoized per (handle, node) inside the plugin.

S11: The compiler child's output is drained while it runs, never only after exit: a child writing more than the pipe buffer must not block and be misreported as a timeout.

S12: Compiling and installing the same graph concurrently is safe: the work files are unique per graph, the cached artifact is written once via an atomic rename, and a lock guards the per-skill install target.

S13 (amends S12): work files are unique per COMPILE, not only per graph: the work directory carries the graph hash plus a per-process and per-call discriminator, so two processes (or two calls) compiling the same graph never share a source or an output path. The cache publish stays atomic, so the last publisher wins and both artifacts are valid.

S14: The dashboard is the entry point for authoring, in two explicit steps: propose (the model drafts a graph JSON from a skill's SKILL.md text, validated before it is shown) and approve (the human submits the reviewed JSON, which is compiled and installed). Nothing is compiled from a graph the human has not seen and submitted.

S14a: A `skill_graph_propose` dashboard action takes a skill slug, reads that skill's SKILL.md, asks the model for a graph JSON, and validates the draft with the same validator compilation uses. It returns the draft graph when it validates, and the validator's message when it does not — a refused draft must explain itself. It never compiles and never writes a plugin.

S14b: A `skill_graph_approve` dashboard action takes the graph JSON the human submitted, validates it, compiles and installs it, and returns whether a compile happened and whether an existing plugin was replaced. The only path to a compiled skill in the dashboard is this action, and it compiles exactly the submitted JSON — it never re-generates, repairs or defaults anything.

S14c: Both actions are additive: every existing dashboard action keeps its current behaviour and response shape, proven by the existing dashboard suite passing unchanged.

S14d: Propose works in a shipped binary, not only under a test seam: the dashboard's own dependency builder wires a live draft function built from the configured provider, the same way the turn judge is wired, so a draft's tokens are metered into the usage ledger like any other model call. When no provider is configured, propose keeps answering its honest "no model backend" error rather than doing nothing silently. Approve needs no model and keeps working with no provider at all.

S15 (revised 2026-11-17, user decision): the loop uses what is installed and never compiles. On a skill match, if `<home>/plugins/<skill>.so` exists and is worker-eligible, the skill runs as a headless worker and its reply is the turn's answer; if it does not exist, the skill body reaches the prompt exactly as today. Compilation is always the explicit dashboard action from S14. Nothing in the loop starts a compiler, so no response ever waits for one and no new concurrency enters the binary.

S15a: A skill with no installed plugin must behave byte-identically to today. The differential proof is part of the task, not an optional extra.

S15b: The worker path fails open: a plugin that raises, is ineligible, or answers an empty reply falls back to the text path within the same turn, and the fallback is visible as a trace line naming the skill and the reason. A compiled skill never makes a turn fail that the text path would have answered.

S15c: The existing gap is closed in the same change: one test asserts a non-empty skill body reaching the system prompt end to end through wireMemory and buildSystem, which today is pinned only in pieces.

S15d: Namespace caution recorded: `<home>/plugins` is loaded in-process at startup, so an installed skill also becomes the graph `plugin:<name>`. A skill whose name collides with an existing plugin shares that name space, and the loop must not assume the installed file is exclusively its own.

S23: A skill run that spends tokens and then raises still books what it spent. Both paths (headless child cost line and in-process skill:<name> ledger row) must emit the accumulated usage even when the run answers nothing, instead of booking nothing.

S24: The skill cache is bounded. skills-compiled keeps only live hashes (LRU/size cap with prune path) and per-compile skills-build work dirs are cleaned, so disk does not grow without bound.

S25: Installing a skill never silently overwrites a hand-written plugin. If <home>/plugins/<name>.so already exists and did not come from the skill cache, approve refuses with a sentence naming the collision instead of replacing it.
